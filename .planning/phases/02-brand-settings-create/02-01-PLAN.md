<objective>
Reduce the v2 settings schema to the v3 minimum (Identity, Design, Focus Areas, Situations, Methods, API Keys) and ship six Firestore-backed settings pages plus a /settings shell. Establish the brand sub-collection model (situations, methods, photos, posts under users/{uid}/brands/{brandId}/) and tighten Firestore rules to enforce per-user scoping plus the aiSnapshot immutability invariant that 02-02/02-03 will rely on.

Purpose: Per ROADMAP Phase 2 success criteria #1 (Identity / Design / Focus Areas / Situations / API keys persist across reload) and #5 (P3 Loyalty pillar, hooks_guidance, strategy, styleTypes, layoutTemplates, removed library tabs do not exist anywhere in the codebase). This plan is the schema + persistence + UI foundation that 02-02 (generate endpoint) and 02-03 (create + editor) read from.

Output:
- shared/schemas/{brand,focusArea,situation,method}.ts as the single source of truth for v3 settings shapes
- Firestore + Storage security rules updated for the new sub-collections + aiSnapshot immutability
- Six settings pages plus a SettingsLayout, all routed under /settings/*
- Helper modules: uploadPhoto, resizeImage, useActiveBrand store
- All schema reductions verified by grep at end of plan (deletions enforced)

This plan does NOT implement: /api/generate (02-02), the create flow (02-03), the zone editor, photo pool gallery (that lands in 02-03), or any rendering. The MethodsPage seeds DEFAULT_METHODS but does not run any prompt-assembly logic - that lives in 02-02.

Path A (locked): Firebase emulators only. No gcloud commands in this plan. Storage uploads target the local Storage emulator; settings reads/writes target the Firestore emulator. Firestore rules + Storage rules are deployed via `firebase deploy --only firestore:rules,storage:rules` against emulator only at this stage; production deploy is Phase 5.
</objective>

firestore.rules update (replace the current strict block; preserves the killSwitch + default-deny):
```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // user root
    match /users/{uid} {
      allow read, write: if request.auth != null && request.auth.uid == uid;

      // brands
      match /brands/{brandId} {
        allow read, write: if request.auth.uid == uid;

        // situations: full CRUD
        match /situations/{sitId} {
          allow read, write: if request.auth.uid == uid;
        }

        // methods: full CRUD
        match /methods/{methodId} {
          allow read, write: if request.auth.uid == uid;
        }

        // photos (pool metadata; binaries live in Storage)
        match /photos/{photoId} {
          allow read, write: if request.auth.uid == uid;
        }

        // posts: aiSnapshot is immutable after create
        match /posts/{postId} {
          allow read:   if request.auth.uid == uid;
          allow create: if request.auth.uid == uid;
          allow update: if request.auth.uid == uid
                        && request.resource.data.aiSnapshot == resource.data.aiSnapshot;
          allow delete: if request.auth.uid == uid;
        }

        // renderJobs (placeholder for Phase 03)
        match /renderJobs/{jobId} {
          allow read, write: if request.auth.uid == uid;
        }
      }
    }

    // legacy nested rule kept as catch-all under /users for paths not enumerated above
    match /users/{uid}/{document=**} {
      allow read, write: if request.auth != null && request.auth.uid == uid;
    }

    match /system/{doc} {
      allow read: if request.auth != null;
      allow write: if false;
    }

    match /{document=**} {
      allow read, write: if false;
    }
  }
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (signed-in user) -> Firestore directly | Client SDK reads/writes brand docs and sub-collections; security rules are the only enforcement layer |
| Browser -> Firebase Storage directly | Photo uploads bypass server entirely; storage.rules enforces per-user scoping |
| Browser -> /api/settings/api-keys (Phase 01 endpoint) | Anthropic key plaintext flows over HTTPS, server KMS-encrypts (or stubs in emulator) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01-01 | Tampering | aiSnapshot mutation by malicious or buggy client | mitigate | Firestore rule `request.resource.data.aiSnapshot == resource.data.aiSnapshot` blocks any update that changes the snapshot. Verified by Task 5 rules test (changed-snapshot update must fail). Belt-and-suspenders: 02-03 client save function only includes `slides`, `caption`, `updatedAt` keys in the update payload. |
| T-02-01-02 | Information Disclosure | Cross-user read of brand / situations / methods | mitigate | All rule blocks pin `request.auth.uid == uid`. Default-deny terminator at the bottom of firestore.rules catches any unmatched path. Task 5 rules test verifies cross-user read fails. |
| T-02-01-03 | Information Disclosure | Cross-user read of Storage objects (photos, logos, situation images) | mitigate | storage.rules `match /users/{uid}/{allPaths=**}` pins to owning user. Direct download URLs from `getDownloadURL()` ARE long-lived signed-ish tokens that grant read to anyone with the URL - acceptable for our use case (URLs are stored only in private Firestore docs, never in publicly-accessible state). |
| T-02-01-04 | Denial of Service | Large image uploads exhausting Storage quota | mitigate | Client-side resize to maxWidth 1080 (situations) / 512 (logo). Browser MIME-type filter on file input. No server-side validation in this phase since uploads bypass server - acceptable at 2-user scale. Bucket lifecycle rules are out of scope for Phase 02. |
| T-02-01-05 | Spoofing | Unauthenticated client writes to settings | mitigate | All rules require `request.auth.uid == uid`. Firestore SDK on client throws on unauthenticated writes. Phase 01 AuthGuard ensures only signed-in users reach settings pages. |
| T-02-01-06 | Repudiation | User claims they never edited X | accept | Firestore writes carry user identity in audit logs (Cloud Audit Logs). Not material at 2-user internal scale. |
| T-02-01-07 | Tampering | MethodsPage seeding race when two tabs load simultaneously | accept | Worst case: 4 default methods get written 8 times via `setDoc` with same id - still results in 4 docs. The setDoc-with-explicit-id pattern is idempotent for the same id, so the race is benign. No mitigation needed. |
| T-02-01-08 | Elevation of Privilege | Storage path injection via subpath param | mitigate | uploadPhoto's `subpath` is constructed by callers from constants ('situations/<sitId>', '', 'photos'). No user-supplied path traversal vector. The storage.rules `match /users/{uid}/{allPaths=**}` enforces the prefix regardless. |
